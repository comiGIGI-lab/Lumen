## 2. ⚠️ 第一件必须处理的事：我自己埋的一个坑

**2026-09-21 我在 nginx 上加了 `client_max_body_size 256k;`** ——
这是当时为了防超大 POST 吃内存加的（那会儿还没有上传功能，所以合理）。

**但一旦实现课件上传，这个值会把文件直接挡掉**，返回 413，请求根本进不到后端。

实现上传时必须同时做三件事：

1. 调大上限（课件建议 `20m`，够用且不至于失控）
2. **按扩展名分别限体积** —— 在应用层做，不要只靠 nginx 一个全局值
3. 保留「非上传接口仍然只有 256k 级」的约束（可以在 nginx 里给上传路径单独开一个
   `location`，用更宽的值，其他路径维持原样）

## 3. 实现建议（按优先级排序）

### ① 上传接口 + 复用现有 PDF/文本解析 ★最高性价比

**做什么**
- 新增 `POST /api/knowledge/import`（multipart/form-data）
- 内部直接调 `document_importer.import_file(path, store=KnowledgeStore())`

**要注意的**
- 现在的 `api_server.py` 是**纯标准库 `http.server`，没有 multipart 解析**。
  两个选择：手写一个 multipart 解析器（约 60 行，够用），或引入框架。
  **建议手写** —— 引入框架会打破「零依赖、开箱即跑」这个现有优势，
  而 multipart 解析是边界清晰的活。
- 文件**不能直接堆在 `data/` 里**。建议 `data/uploads/<内容hash>/`，
  好处是天然去重（同一份课件传两次不占两份空间），而且方便做配额。
- 现有的 `import_file()` 是**同步阻塞**的。一个 20MB 的 PDF 解析可能要十几秒，
  会把那个请求线程占住。当前 `ThreadingHTTPServer` 还能扛，但必须加超时保护。

**工作量**：中等偏小 —— 大头是 multipart 解析和文件存储，解析逻辑直接复用。

### ② OCR：选型是唯一决策点，代码已经现成

**关键约束：你们的服务器只有 1.6GB 内存。**

| 方案 | 磁盘 | 内存 | 评价 |
|---|---|---|---|
| `easyocr` | **约 2GB**（连带 torch） | 高（torch + 模型常驻） | ❌ **不要在这台机器上用**。而且你之前刚担心过"会不会爆" |
| `tesseract` | 约 50MB | 轻 | ✅ **推荐**。`apt install tesseract-ocr tesseract-ocr-chi-sim` 即可，`_extract_with_tesseract()` 直接能用 |
| 云 OCR API（腾讯云/百度等） | 0 | 0 | ✅ 可选增强：精度更好、零本地占用，按量计费 |

**建议组合**：tesseract 打底（保证离线可演示）+ 云 API 可选（答辩时演示高精度）。

**注意**：`screenshot_ocr.py` 里已经写好了 `is_ocr_available()` / `get_backend_name()`，
前端可以直接读这两个状态来显示「OCR 可用 / 未安装」——**别让用户点了一下才发现不可用**。

### ③ 检索质量：先修「命不中」，而不是上向量

这是**当前最真实的痛点**，而且和向量无关：

`knowledge_store.search()` 拿**整个问题**去 `in` 标题/正文/标签。实测：
- 「索引失效的常见情形」→ ✅ 命中（因为和笔记标题几乎一字不差）
- 「费曼技巧是什么」→ ❌ 不命中（就多了「是什么」）

**最小改动方案**：整句不命中时降级 —— 按 2-4 字滑窗拆词，
按命中词数 × 位置权重打分，取超过阈值的第一条。约 30 行，**零新依赖**。

对比：上向量要先解决 embedding 从哪来（据我所知 DeepSeek 的 chat API 不提供 embedding
接口，这点你们需要确认），再引入向量库或手写余弦相似度。
**在 20~500 条笔记这个量级，向量检索相对关键词加权的收益非常有限。**
先把 ③ 做掉，④ 视时间决定。

### ④ 分块 + 向量索引（可选，建议赛后）

如果确实要做（比如为了答辩讲"向量检索"这个点）：

- **不要装向量库**。几百条笔记，用 numpy 算余弦相似度就够快；
  甚至纯 Python（`math` + 列表推导）在这个量级也完全够。
- **embedding 来源要先确认**。可选：本地小模型（如 BGE-small，约 100MB）、
  或某家提供 embedding 接口的云服务。**这一步没定，别开工。**
- 分块策略：语义分块听起来高级，但实现上是「按标题层级 + 长度阈值」的规则切分，
  不需要模型。建议按 `##` 标题切，再对超长段落按句边界二次切。
- **注意与现状的冲突**：现有的 `document_importer` 是「抽关键句 → 一条笔记」，
  而分块是「切成 N 片 → N 条记录」。这两套要统一，否则知识库里会出现
  同一种材料两种形态。**先定数据模型，再写代码。**

### ⑤ 进度与重试：复用已有的 SSE 基建

**别新发明一套。** `/api/plan/stream` 那套 SSE 已经验证过：
事件渐进推送、Nginx 已关 `proxy_buffering`、前端有现成的消费代码模式。

- 上传后返回 `job_id`，前端用 `EventSource` 订阅
  `GET /api/knowledge/import/stream?job_id=xxx`
- 任务状态落 `data/jobs.json`（进程重启不丢，也和现有存储风格一致）
- 重试 = 按 `job_id` 或文件 hash 重新入队；因为文件按 hash 存，**重试不重传**

## 5. 建议的推进顺序

| 顺序 | 事项 | 依赖 | 风险点 |
|---|---|---|---|
| 1 | 上传接口 + 复用 PDF/文本解析 | 无 | **必须先调 `client_max_body_size`**（见 §2） |
| 2 | tesseract OCR 接入 | 服务器装包（约 50MB） | 新版 EasyOCR 不能上这台机器 |
| 3 | 检索改关键词加权 | 无 | 注意别把「枪械设计原理」这类合法词误伤（可参考敏感词表的组合词思路） |
| 4 | 进度 / 重试（复用 SSE） | 1 完成 | 任务状态要持久化 |
| 5 | 分块 + 向量索引 | **embedding 来源要先定** | 数据模型要与现有"关键句"形态统一 |

**1 和 3 是性价比最高的两项**：都不引入新依赖，都能明显提升可演示性。
