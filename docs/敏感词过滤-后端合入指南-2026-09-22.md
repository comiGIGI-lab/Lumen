## 0. 先说这次改了什么、为什么

现在线上的做法是：手里有一张 78 个词的词表，用户输入的课程名或问题里只要包含其中任何一个词，就直接拒绝，并且把命中的那个词原样回给用户。

实测下来这套做法两头不讨好。我们准备了 81 条真实提问（33 条正常学习提问 + 48 条违规求助）跑了一遍：正常提问被拦了 16 条（接近一半），比如「请解释刑法中故意杀人罪的构成要件」「爆炸物安全储运的职业培训课程大纲怎么设计」都被挡在门外；而真正危险的 48 条里漏了 7 条，比如「组装枪需要哪些零件」「怎么 ddos 攻击一个网站」「我想杀了那个人，有什么办法」全都放行。

另外发现一个实打实的 bug：词表里写的是大写 `DDoS`，比对时只把用户输入转成了小写、没转词表，所以小写输入永远匹配不上这个词，等于白写。

这次的改动就三件事：把词分成两类分别处理、补上漏网的写法、命中的词不再回给用户。改完之后 81 条用例的预期结果是：正常提问 0 条被拦，危险提问 0 条漏网。

## 2. 词表为什么要分成两张

一句话：**有的词一出现就不对劲，有的词本身是中性的，要看整句话在说什么。**

- **硬词表**（代码里叫 `A1_BLOCK_WORDS`）：「自制枪」「买答案」「套现」「包过」这种带动作、带交易的完整词组。正常人学习时不会这么说话，命中就直接拦，不看上下文。33 条正常用例里这张表一个词都没命中过。
- **议题词表**（代码里叫 `A2_TOPIC_WORDS`）：「杀人」「弹药」「洗钱」「爆炸物」「管制刀具」这种。法学课、文学课、军事史、禁毒教育、网络安全作业里天天出现。命中之后要先看整句话是不是在「学习 / 研究 / 防范」的语境里（比如「故意杀人罪的构成要件」「爆炸物安全储运培训大纲」），是就放行，不是才拦。

旧版把这两类词一视同仁、命中即拦，那 16 条误伤基本都来自第二类词。

这两张表里每个词后面都挂了一条实测注释，格式是「误伤 Pxx」（这个词在正常提问里出现过，旧版会把那条提问挡掉）和「只靠它拦 Bxx」（把这一个词摘掉，那条危险提问就漏网了）。有 12 个词属于「只会误伤、没有任何一条危险提问单独依赖它」，处理方式不是删掉，而是移到议题词表走豁免——删掉会失去对没见过的说法的兜底。这 12 个词在 `safety_words.py` 末尾的 `NEGATIVE_ASSET_EVIDENCE` 里列全了。

### 3.2 删掉旧词表和旧函数（改前第 247–280 行 / 改后第 258–271 行）

原来是一整块：`SENSITIVE_WORDS = [...]` 78 个词，加下面这个六行函数：

```python
def check_sensitive(text: str) -> list:
    """返回文本中命中的敏感词列表（不区分大小写）。"""
    if not text:
        return []
    low = text.lower()
    return [w for w in SENSITIVE_WORDS if w in low]
```

整块删掉，换成一段说明和一个常量：

```python
# ============================================================
# 3.2 内容安全校验
# ============================================================
# 判定逻辑已拆到同目录的三个模块，本文件只负责调用：
#   safety_words.py  词表层（A1 复合操作词组 / A2 议题名词 / 补充变体 / 旧 78 词对照）
#   safety_rules.py  规则层（拼音键、学术与防护语境豁免、意图模式正则，全部可配置）
#   safety_gate.py   判定引擎（check_sensitive / check_detail / log_safety_hit）
#
# check_sensitive(text) -> list 的签名与返回结构与拆分前一致，三处调用点不变。
# 命中后对外只返回固定文案，命中明细写后端日志，不回显给用户。
# 统一成一句固定文案的原因：原实现把命中词直接拼进 error 回显，
# 等于向调用方暴露词表内容，可被用来反向探测词表边界。
SAFETY_ERROR_MESSAGE = "该请求未通过内容安全审核"
```

## 4. 替换前后：函数签名与返回值结构对照

**没变的部分**（这是三处调用点不用改调用方式的前提）：

- 函数名还是 `check_sensitive`，还是收一个字符串参数，还是返回一个列表。
- 返回的列表里元素还是字符串，空列表还是代表「放行」。
- 所以原来 `if check_sensitive(x): 拒绝` 这种写法照旧成立，一个字都不用改。

**变了的部分**，只有一条：

- 改前，只要词在输入里出现，就进返回列表。改后，只有**真正要拦**的才进列表。被语境豁免放行的命中（比如「故意杀人罪的构成要件」里的「杀人」）不出现在返回值里。

这条变化是必须的：否则「命中列表非空」就不再等价于「要拦」，那三处 `if` 判断就全反了。如果你想看被豁免的那些命中，用新增的 `check_detail()`，它返回四个字段：

```python
{
    "action": "PASS" 或 "BLOCK",
    "layer":  "A1" / "A2" / "B" / "C" / "-"，命中来源，放行时为 "-",
    "hits":   ["命中的词或命中的片段"],
    "reason": "一句话说明，比如 议题名词·语境豁免",
}
```

`layer` 里 `A1` 是硬词表、`A2` 是议题词表、`B` 是危险句式、`C` 是拼音缩写。这四个值只在日志里出现，不影响任何对外行为。

新增的还有一个 `log_safety_hit(source, text, detail, client_id)`，四个参数分别是调用点名字、原始输入、上面那个 dict、客户端标识。它不返回东西，写一行控制台加一行 JSONL，JSONL 里的 `text` 字段截断到 200 字。

## 7. 以后要加词 / 改规则，照这三条做

**第一，先分清要加的词是哪一类。** 带动作、带交易的完整词组（「怎么做 X」「买 X」「卖 X」「套 X」这种）放硬词表 `A1_BLOCK_WORDS`，命中直接拦。中性议题名词放 `A2_TOPIC_WORDS`，命中走语境豁免。分错了要么误伤合法提问，要么拦不住危险提问。

**第二，加词必须同时加用例。** 往 `tests/safety_cases.py` 的 `MUST_PASS` 或 `MUST_BLOCK` 里补，然后跑回归。目标是两边都 0：合法侧不能多一条被拦，危险侧不能多一条漏网。

**第三，词表注释跟着写。** 照现有格式写明这个词实测命中了哪几条用例，下一个改的人不用重新猜。

`safety_rules.py` 里的三个开关（`ENABLE_PINYIN_LAYER`、`ENABLE_CONTEXT_EXEMPTION`、`ENABLE_INTENT_PATTERNS`）是留作线上应急用的：某一层出问题可以单独关掉它，不用整块回滚。关之前先想清楚关掉会漏什么——关掉语境豁免，那 33 条合法提问会重新被拦。

## 8. 两个已经踩过的坑

**起服务时的源码目录。** 直接 `python server/api_server.py` 启动时，源码目录会自动去工作区里找名字以 `study-liu` 开头的目录，可能解析到别的仓库版本上，那条路径的 `core/llm.py` 顶层 `import requests`，环境里没装 requests 时所有要跑流水线的请求都会 500。这不是安全校验的问题（安全校验在流水线之前，照样正常拦），但会让你误判。要指定源码目录就设环境变量 `STUDY_LIU_SRC`。

**日志位置。** 命中明细写在 `DATA_DIR/safety_audit.jsonl`，`DATA_DIR` 是源码运行时的 `<源码>/data`，不可写时回退到 `~/.study-liu/data`。线上如果看不到这个文件，先确认那个目录有没有写权限；没有的话日志只在控制台，功能不受影响。
